### 补充：下午（L2 / mini Pi 深化 · 人-Agent 协作 + loop 机制）

**1. 配置 Codex 做 GitHub issue/PR 协作流（真·HITL 雏形）**
- 流程：我开 issue 定义新功能 → Codex 据 issue 提 PR → 我做 review。
- 价值：把"人和 Agent 的职责"从模糊变清晰——每个新功能必须有一个独立 issue 来判定边界，项目结构更清楚，也天然形成"提案可提、执行前必须人审"的 HITL 模式（对应 Phase 8 Human-in-the-Loop）。
- 这是 agent 工程里最容易被忽略但最值钱的一步：**先定协作契约，再让 Agent 干活**。

**2. 探究 agent 内部机制分层**
- 你梳理的链：接收用户信息 → 变成结构化 prompt → 思考/考虑工具调用编排 → 走完一个循环。
- 引出实验想法：loop 有很多实现方式（ReAct / sub-agent / 并行 …），想知道 **agent 如何评估"何时用哪种方式"去探索或执行任务**。

**3. 关键辨析（立 ⬜）**
- 你的疑问隐含一个前提："agent 自己决定用哪种 loop 模式"。但当前主流 agent 里，**控制流模式（ReAct/sub-agent/并行）通常是设计者硬编的确定性脚手架**，agent 只在模式内部决定 tool 调用。这正好是 Phase 4（Workflow/Orchestration）的核心问题——**哪些决策交给 LLM、哪些留给确定性流程**。你的实验若想清楚这一点，会比"测哪个模式更强"更有价值。
