## 上午（L5 英语 · 口语流利度与句子扩展法）

流利度这块，先别急着说完整长句，从核句（kernel sentence）起步，靠重复和逐步加从句长出来。你举的链很直观：`I'm curious.` → `I'm curious about things.` → `I'm curious about things because...` → `...which can make me...`。多练、多重复，从简单句慢慢长，而不是硬憋复杂句。

顺手纠两个语法点：
- `I'm a curious` 不对，curious 是形容词，不能加 a，要写 `I'm curious`（想要名词就说 `I'm a curious person`）。
- `which can makes me` 不对，can 后面接原形，应该是 `which can make me`。
- `and which` 得理清先行词，更干净写法是 `I'm curious about things, which can make me...`（一个 which 引导非限制定语从句），或者 `...because X, and this makes me...`。

这套"核句→加 because/which 分支"的扩展法本身就是流利度训练的有效路径，能降认知负荷、建立句型肌肉记忆。

而且它正好能被你昨天想的"场景式英语 APP"产品化：用户输入一个核句，APP 引导加 because / which 分支，生成扩展句并跟读。L5 的产出探索和主航道就这么接上了。

## 上午（续 · L1 Pi Agent · agent loop 与异步机制，约 4 小时）

读了 Pi Agent 的 agent loop 核心，重点在异步 think 机制。Promise / await 的基本用法你抓到了：调用一个"稍后才有结果"的操作（比如 LLM 返回、工具 I/O）时，用 await 把当前函数挂起，等结果回来再继续。你自己的比喻很准：像餐厅，客户到前台点单，前台把单子交给厨房（异步操作），挂起一个 promise 进入 await，主线程不阻塞、继续接下一单；厨房做好（promise settle）再回调续做。目标就是让子任务 / I/O 不阻塞主线程。

但这里有个关键细节得订正：JS/TS 的主线程是单线程的，async/await 并不会创建新子线程。它靠事件循环（event loop）加微任务队列（microtask queue）实现非阻塞，不是多线程并发。精确过程是：async 函数同步执行到 await 时，挂起自身（返回一个 pending promise），把控制权交还事件循环，事件循环转去跑别的已就绪任务；等被 await 的 promise settle，续写部分作为微任务排进队列、择机恢复。你嘴里的"厨房"在 Node/浏览器里通常是运行时的 I/O 子系统（底层可能用线程池做网络/文件），但那段不是你的 JS 主线程；CPU 密集的活想真并行得用 Web Worker / worker_threads，不是 await。

所以你那句"不让子线程阻碍主线程"该改成"不让 I/O 等待阻塞主线程"：await 释放的是主线程的当前调用栈，不是 spawn 线程。agent loop 必须异步，是因为每轮都要 LLM 网络往返加工具调用（一堆 I/O），全 awaitable；要是同步写，等 LLM 时整个进程卡死，await 让事件循环在等 LLM 时空出来。

卡点记在顶部了：事件循环、微任务 vs 宏任务、await 挂起-恢复这条完整链路。你自述"只是基本了解概念、很多不清楚"，符合 active learning 捕获条件。

回头自己手写一个 async 函数加 console.log 顺序实验，验证 await 前后代码的执行顺序和微任务排队行为（错题本，hand-write）。再回 Pi Agent 源码，定位 agent loop 里实际 await 了哪些调用（LLM / tool / sleep），对照着理解。
