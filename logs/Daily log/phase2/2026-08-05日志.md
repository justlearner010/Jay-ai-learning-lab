### Agent 笔记：本次概念纠正（重要，防以后重复错）

你口述有两个点要纠偏。

第一，前向传播的顺序说反了。你说的是 input → ReLU（把小于 0 的变 0）→ 再加权重 W 和偏差 b → 得到数据。正确的是 input x → z = W·x + b（线性变换，先做）→ a = ReLU(z)（激活，后做）→ 输出或下一层。权重和偏差作用在激活之前，ReLU 作用在 Wx+b 的结果 z 上。你描述的"先 ReLU 后 Wb"在数学上不成立，ReLU 是对加权求和加偏置之后的值做门控。

第二，ReLU 的作用定位错了。你说 ReLU 把小于 0 的变 0 是为了减少 noise（噪音）。纠正：ReLU 的核心目的不是降噪。它是非线性激活函数，作用有三：引入非线性（没有它，多层线性变换叠起来还是线性，学不了非线性边界）；缓解梯度消失（x>0 时梯度恒为 1，对比 sigmoid 两端梯度接近 0，训练更深更稳）；顺带产生稀疏性（很多神经元输出 0），稀疏可以看成一种轻量正则或效率，但这不是降噪。把负数砍成 0 是 ReLU 的数学定义，不是它降噪的手段。

说对的部分确认无误：一个输入连多个隐藏单元 H，再到不同输出 y（全连接层里每个隐藏单元有自己的一组 W 行加 b），这是多层感知机 / 多输出的正确直觉。dying ReLU：大量神经元输入恒为负，输出恒 0，梯度也恒 0，参数永不更新，神经元死掉。你理解对了。Leaky ReLU：x<0 时给一个很小斜率 α（比如 0.01），f(x)=αx，让负值接近 0 但不为 0，梯度非零，神经元可复活。你也理解对了。

总得来说，架构直觉、dying ReLU、Leaky ReLU 都懂了；卡在"前向顺序"和"ReLU 本职"两个点，已经立 ⬜ 卡点。闭环动作是 hand-write 最小前向传播验证顺序。

### Agent 笔记：下午 Pi Agent 架构梳理（L1，与 8/4 五层对照）

你下午把 8/4 拆出的 5 层（Core Loop / tools / Event Stream / LLM provider / 消费流）收敛成更清晰的三层加独立 TUI：

1. Pi-AI 层（最底层）：对接 provider，负责实际 AI 模型调用。约等于 8/4 的 LLM provider 层。
2. 循环层（Loop layer，中间）：只负责 agent loop 每一步编排，接收任务、工具编排、调用、把结果交给下面的 LLM 判断、决定是否继续循环。约等于 8/4 的 Core Loop 加 tools 加 Event Stream 加消费流，打包进这一层。
3. CLI + SDK 层（最顶层）：暴露给外部使用的接口。
4. TUI 层（terminal UI，独立）：和上面三层解耦，意味着可以自己接 GUI，或者把 SDK 嵌进网页。因为 SDK 已经外暴露，你能基于它写自己的 agent。

设计哲学这块你的洞察对，也值得记：Pi 把能删的都删了（MCP、plan mode、各种插件），只保留 agent 最基础也最完整的能力。这和 Claude Code 的全包式相反，Pi 给的是裸但高级的基础框架，鼓励用户自己探索扩展（MCP / plan / 自定义）。它的优势来源很清楚：因为极简，system prompt 短（没有 MCP 协议那类系统提示词），某些任务上响应更快。

还有一点没闭环（不立卡点）：8/4 的"消费流"卡点今天还没正面回答。今天讲的是三层加 TUI 的对外接口和分层，而消费流是 Event Stream 之后谁来接住事件。现在看，消费流很可能就是循环层内部把 Event Stream 喂给 TUI 或外部消费者的那段。建议下次读 Pi 源码时专门确认 consumer / subscribe 在循环层还是 TUI 层。该卡点维持 ⬜。

Pi 的分层现在立住了，三层加一个 TUI。比起 8/4 那五个散开的层，这次算是看清了骨架。消费流具体落在哪，还得翻开源码才算数。
