# 待验证假设

本页记录可以被观察或实验否定的命题，不把对话中的直觉当成已经成立的事实。

## H1：持续监控主要来自不确定性

**命题**：用户反复查看 Agent，主要不是因为执行日志有价值，而是不确定自己是否会被需要、Agent 是否仍在正常运行。

**可观察信号**：

- 等待期间的进度查看次数；
- 每次查看的理由；
- 已知“暂时不需要人”后查看频率是否下降。

## H2：可靠的召回承诺比精确 ETA 更重要

**命题**：相比更精确的剩余时间，“必要时一定召回你，并说明原因”更能让用户释放注意力。

**支持证据**：有可靠通知时，用户更少轮询、更愿意离开，即使 ETA 仍是范围。

**反证**：加入可靠通知后，轮询行为与主观焦虑没有变化。

## H3：关键事件足以覆盖大多数有价值介入

**命题**：任务开始、需要决策、出现异常、任务完成这四类事件，可以覆盖多数真正需要人类注意力的时刻。

**待检验问题**：

- 是否缺少“关键里程碑”这种不需要立即决策、却有助于校准信任的事件？
- 权限请求应归为决策还是异常？
- 高风险任务是否需要独立事件类型？

## H4：通知的价值取决于信息质量

**命题**：只有“Agent 停下了”的通知不足以支持人的决策。有价值的召回至少应说明：

1. 发生了什么；
2. 为什么需要人；
3. Agent 已经尝试了什么；
4. 有哪些选项及取舍；
5. Agent 推荐什么；
6. 不处理会造成什么后果。

## H5：微任务不是所有等待的默认答案

**命题**：在许多场景中，“可以放心离开”或“休息并等待召回”比生成一个上下文微任务更好。

**可能例外**：当用户明确希望保持当前认知状态，且等待时间较短时，与验收直接相关的可中断思考可能有价值。

## H6：信任应随任务而不是随 Agent 品牌设定

**命题**：同一个人对同一 Agent 的监控需求，会随任务风险、可验证性、熟悉程度和可逆性变化。

可能的输入维度：

- 结果错误的成本；
- 操作是否可恢复；
- 是否有自动测试或其他闭环验证；
- 用户对当前领域的熟悉程度；
- Agent 过去在相似任务中的可靠性。

## H7：多 Agent 系统的价值在于边界与聚合，不在于角色数量

**命题**：多 Agent 只在任务能够独立拆分、信息能被压缩聚合、责任和升级路径清晰时，才会降低人的管理成本。

**反证**：加入中层 Agent 后，沟通、冲突和验收成本高于直接管理单个执行 Agent。

## 当前核心假设

第一阶段只验证 H1 和 H2。H3–H7 保留在孵化池中，不将它们同时变成开发需求。
