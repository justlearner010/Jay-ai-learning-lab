# Agent Attention Routing

> 从“持续盯着 Agent”转向“只在关键节点召回人”的人机协作实验。

## 当前状态

- 阶段：想法孵化 / 问题验证
- 当前不做：不立即开发完整产品，不预设 IDE 插件、菜单栏应用或 Agent 协议等最终形态
- 当前目标：先确认“人为什么无法放下正在执行的 Agent”，以及可靠的关键事件通知能否改变这种行为

## 项目起点

使用 Agent 时，人经常会盯着 `Thinking...`、工具调用和测试日志。表面上是在“等待”，实际上更像处于低强度的持续监控状态：

- 不知道 Agent 何时完成；
- 不知道它何时会需要权限、方向或其他决策；
- 担心它理解错误、陷入循环或因异常停下；
- 离开后可能错过需要人介入的时刻。

因此，人虽然没有在亲自执行任务，注意力却仍然被 Agent 占用，既不敢进入另一项高认知负荷活动，也没有真正休息。

## 核心问题

> 用户持续监控 Agent，是否不是因为监控本身有价值，而是因为当前系统缺少可靠的中断机制和经过校准的信任信号？

如果这一判断成立，真正需要设计的就不是“等待时推荐什么小任务”，而是：

> 如何把人与 Agent 的协作从持续轮询（polling）改造为事件驱动（event-driven）？

## 核心构想

Agent 正常执行时，人不需要持续查看它的“思考日志”。系统只在注意力真正有价值的关键节点召回用户：

1. **任务开始**：确认目标、边界、预计时间范围和介入规则。
2. **需要决策**：Agent 遇到了它不应自行替人取舍的方向问题。
3. **出现异常**：网络、权限、工具、测试、循环或高风险操作使执行无法正常继续。
4. **任务完成**：给出结果、风险、假设和需要人验收的内容。

这些事件之外的执行细节默认保持安静，但底层日志仍可在调试或低信任状态下查看。

## 人与 Agent 的定位

这个构想里，人不是监工，Agent 也不是为结果承担最终责任的外包公司。

### 人负责

- 定义项目目的、服务对象和成功标准；
- 设定约束、优先级和不可逾越的边界；
- 对不同方案进行取舍；
- 验收结果并承担决策后果。

### Agent 负责

- 根据已确定的目标和边界拆解、执行和验证任务；
- 处理正常执行中的细节；
- 识别自己没有被授权决定的问题；
- 在异常、风险或需要取舍时向人升级。

这不否定执行层能力的价值。人要设计、判断和验收一个技术系统，仍然需要通过实际学习和项目练习建立对细节的理解。执行与决策是不同维度，不是一个可以用大于号排序的选择。

## 信任过渡与产品边界

这个项目主要服务于 Agent “尚未完全可信，但已经能承担较长执行”的过渡阶段：

```text
完全不信任
  -> 持续监控
  -> 关键节点监控    <- 当前项目边界
  -> 通知驱动
  -> 高度自主委托
```

未来 Agent 如果能以足够高的可靠性完成所有执行，“等待期注意力调度”可能会缩小。但以下问题仍可能持续存在：

- 什么任务可以放权；
- 哪些风险必须由人复核；
- Agent 何时应该升级问题；
- 多个 Agent 的信息如何分层汇报。

因此，它可能从 **Attention Routing** 演化为 **Trust Calibration**，最后进入更广泛的 **Human–Agent Coordination**。这是可能的发展路径，不是当前已确定的产品规格。
