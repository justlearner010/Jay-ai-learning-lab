# 最小验证计划

## 实验目的

在开发产品前，先验证两个最底层的问题：

1. 自己在 Agent 执行时是否真的处于低强度持续监控？
2. 如果确信“需要你时会可靠召回”，自己是否能更放心地释放注意力？

暂时不验证产品形式、通用微任务生成、多 Agent 组织层级或商业模式。

## 阶段 A：自然观察

先记录 10–20 次真实 Agent 执行间隔，不主动改变自己的行为。

### 每次记录

```text
日期与时间：
主任务：
Agent 工具：
Agent 正在做什么：

事前预计等待：
实际等待：
任务风险：低 / 中 / 高
结果是否容易验证：是 / 否

等待期间做了什么：
为什么选择这么做：
主动查看进度的次数：
每次回来查看的原因：
是否担心错过权限 / 决策请求：

Agent 完成后多久开始有效验收：
是否重新阅读了目标或需求：
是否发现 Agent 的问题：
主观紧张或悬置感（0–5）：
其他观察：
```

### 阶段 A 结束后只回答

- 我的“等待”中有多少次实际是在轮询？
- 我真正担心错过的是什么？
- 哪些任务我可以放下，哪些任务不能？
- 是等待时长、任务风险，还是通知不可靠更能解释行为？

## 阶段 B：两条件交替对照

在条件尽量相似的 Agent 任务中，交替使用两种方式，每种至少记录 5 次。

### 条件 A：自由等待

- 保持现有 Agent 界面和通知方式。
- 自由决定是否查看进度、离开或做其他事情。

### 条件 B：明确召回协议

在 Agent 开始时先确认：

```text
当前任务目标：
当前阶段：
预计时间范围：
这一阶段是否预计需要人输入：
会召回人的事件：决策 / 异常 / 权限 / 完成
召回时需要说明：停止原因 + 已尝试内容 + 需要人做的事
```

如果当前工具不能真正保证通知，必须如实记录，不把一个文字承诺当成已经实现的机制。

## 核心指标

### 主指标

- 等待期间主动轮询次数。
- 用户是否愿意离开 Agent 界面。
- Agent 完成后到开始有效验收的时间。

### 次指标

- 是否错过了真正的介入请求。
- 通知是否在不必要时打断了用户。
- 回归主任务后是否忘记原始目标或约束。
- 对 Agent 输出的错误发现情况。
- 主观焦虑、控制感与通知疲劳。

## 第一轮决策规则

### 继续孵化

当条件 B 出现以下组合时，才考虑设计交互原型：

- 轮询次数明显降低；
- 没有增加错过关键介入的风险；
- 用户对离开界面更放心；
- 回归后的验收表现没有变差。

### 修正假设

如果轮询主要由任务学习需求、娱乐性或高风险审核驱动，则不应继续假设“可靠通知”是通用答案。

### 停止开发

如果可靠召回既不减少轮询，也不改善主观状态，则先停止产品化，保留这份观察作为负面结果。

## 不在第一轮做的事

- 不训练 ETA 预测模型。
- 不自动读取多家 Agent 的内部日志。
- 不生成通用微任务库。
- 不搭建多 Agent 公司式层级。
- 不设计完整的桌面或 IDE 产品。
- 不用“填满了多少时间”作为成功指标。
