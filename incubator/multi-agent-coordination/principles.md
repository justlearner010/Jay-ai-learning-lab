# 设计原则

## 1. 先有真实复杂度，再增加 Agent

只有当任务可以被独立拆分、结果可聚合，或单 Agent 明确受到上下文、工具或专业边界限制时，才增加 Agent。

## 2. 每个 Agent 只拥有最小必要权限

任务边界与工具权限应一致。不因为 Agent “可能用得上”就给它整个系统的写入权。

## 3. 默认不越界

发现相关但不在当前合同内的问题时，Agent 应记录并上报，而不是擅自扩大任务。

## 4. 交付结果必须同时交付证据

“我完成了”不是可验收的状态。子任务必须提供测试、产物、数据、引用或其他能够被独立检查的证据。

## 5. 过滤信息，但不销毁信息

Coordinator 可以压缩底层日志，但必须保留下钻到原始证据的路径。否则“管理层汇报”会变成不可审计的单点真相。

## 6. 正常状态安静，例外状态升级

人的注意力用于目标歧义、高风险操作、边界冲突、无法验证与最终验收，不用于持续轮询普通进度。

## 7. 协调者不是绝对可信的

Coordinator 的拆解、摘要和验收本身也可能错误。系统必须保留原始证据、明确不确定性，并允许人或验证机制检查 Coordinator。

## 8. 独立验证优先于 Agent 互相说服

如果问题可以用测试、类型、规则、模拟或真实数据检查，优先使用确定性验证，而不是让更多 Agent 投票。

## 9. 冲突应暴露，不应被自动一致性掩盖

多个 Agent 给出不同结论时，Coordinator 应报告分歧、证据和取舍，不应为了让汇报看起来稳定而制造虚假共识。

## 10. 系统稳定优先于表面并行

如果并行执行带来更多状态冲突、重复劳动和合并成本，就应减少并行度或回到单 Agent。

## 11. 人的责任不因层级增多而消失

层级可以压缩信息、分配任务，却不能替人承担现实后果。人仍然必须理解项目的关键风险与验收标准。

## 12. 每增加一层，都必须证明它减少了什么复杂度

新层级至少应在信息量、冲突、验收、权限隔离或失败恢复中解决一个真实问题。无法证明时，就应删除这一层。
