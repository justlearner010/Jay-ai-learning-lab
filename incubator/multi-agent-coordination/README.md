# Multi-Agent Coordination

> 通过分层协调、信息过滤、权限边界和异常升级，让人能够以更低的认知负担管理多个 Agent，并让整个系统执行得更稳定。

## 当前状态

- 阶段：未来项目方向 / 想法孵化
- 预计位置：Phase 5 或更后
- 当前不做：不立即实现多 Agent 平台，不预设框架，不用 Agent 数量作为项目进度
- 进入条件：先在 Phase 4 完成一个可靠的单 Agent 或 AI 系统闭环

## 学习路线中的位置

```text
Phase 3：机制原理
  理解 Transformer 如何计算与学习
          ↓
Phase 4：最小应用与系统工程
  构建能调用工具、维护状态、处理失败和闭环验证的单 Agent
          ↓
Phase 5+：复杂系统与协调
  研究多 Agent 的责任边界、信息过滤、分层协调和异常升级
```

这是一条从机制到应用、再到复杂系统的自然路线。多 Agent 不是为了绕过基础能力，而是在理解单个 Agent 的运行边界后，进一步学习如何设计一个由多个执行者组成的稳定系统。

## 项目起点

当一个人同时管理多个 Agent 时，如果每个 Agent 都直接汇报所有计划、日志、问题和结果，人很快就会成为系统的信息瓶颈。

对话中形成的核心直觉是：

> 人不需要管理每一个执行 Agent，而应该管理少数负责协调、验收和信息过滤的 Agent。

这与传统组织中的层级有相似之处，但不能简单复制“CEO—经理—员工”的职位名称。层级只有在它真正承担任务拆解、权限管理、状态聚合、质量验收或异常升级时才有价值。

## 核心问题

> 分层协调和信息过滤，能否比扁平多 Agent 协作减少人的中断、冲突与重复劳动，同时提高任务执行的可预测性、可验证性和失败恢复能力？

## 候选系统结构

```text
Human
  │  目标、约束、重大取舍、最终责任
  ▼
Coordinator Agent
  │  任务拆解、权限分配、共享状态、普通冲突处理、信息压缩
  ├── Specialist Agent A
  ├── Specialist Agent B
  └── Verification Agent
         证据检查、约束验收、反例与风险报告
```

这只是待验证的最小层级，不是预设的最终架构。如果一个 Coordinator 不能带来明显收益，就不应继续添加更多“中层”。

## 人应保留的权力

- 定义为什么做、为谁做和什么算做好；
- 确定不可逾越的安全、成本、时间和价值边界；
- 对重大方向冲突做取舍；
- 决定哪些操作可以授权；
- 对最终产物验收并承担后果。

这对应的人类角色不是“监工”，而是设计系统、配置权限和管理例外的负责人。

## 与 Agent Attention Routing 的关系

[`Agent Attention Routing`](../agent-attention-routing/README.md) 研究单个 Agent 何时值得召回人。本项目将这个问题扩展为：

- 执行 Agent 应该向谁汇报；
- 哪些问题由 Coordinator 解决；
- 哪些问题必须升级给人；
- 多个 Agent 的状态如何压缩成可决策的汇报；
- 信息过滤如何避免同时变成信息隐藏。

## 不是什么

- 不是让多个 Agent 在群聊里自由讨论。
- 不是把相同模型贴上不同职位名称。
- 不是假设 Agent 越多，结果就越好。
- 不是让协调 Agent 代替人决定项目的最终目标和价值取舍。
- 不是在单 Agent 还不稳定时，通过增加协作层掩盖基础问题。
