# 分层协调模型

## 层级不是身份，而是职责边界

设计多 Agent 层级时，不先问“它叫什么职位”，而先问：

- 它接收什么输入；
- 它有权决定什么；
- 它必须交付什么；
- 什么情况下必须停止并升级；
- 谁来验收它的结果。

## 最小层级

### Human：责任与方向层

**输入**：现实目标、用户需求、资源、风险与价值判断。

**责任**：

- 定义目标与验收标准；
- 设定授权范围；
- 处理重大方向冲突；
- 承担最终决策后果。

**不负责**：持续查看每个 Agent 的工具日志和普通执行细节。

### Coordinator：协调与信息层

**输入**：人给出的目标、约束、授权与验收标准。

**责任**：

- 将任务拆成边界清晰、可独立验证的子任务；
- 为各 Agent 分配最小必要权限和上下文；
- 维护一份结构化共享状态；
- 检查子任务交付物是否有证据；
- 解决授权内的普通调度与冲突；
- 将底层状态压缩成面向人的决策汇报；
- 将超越权限的问题升级。

**不负责**：自行改写人设定的最终目标、安全边界或价值取舍。

### Specialist：执行层

**输入**：子任务合同、必要上下文、工具权限与完成标准。

**责任**：

- 在明确边界内执行；
- 交付结果、证据、假设和未解问题；
- 出现边界冲突或无法验证时停止并上报。

**不负责**：为了完成局部任务而擅自修改其他 Agent 的交付物或系统全局目标。

### Verifier：独立验证层

**输入**：验收标准、交付物、执行证据与风险边界。

**责任**：

- 用测试、规则、反例或第二视角检查结果；
- 区分“有证据通过”、“有条件通过”和“无法验证”；
- 报告风险而不篡改业务目标。

验证者是逻辑角色，不一定必须由独立模型实例承担。当独立 Agent 没有提高错误发现能力时，可以改用确定性测试或规则。

## 四种必须分开的流

### 1. 任务流

```text
目标 -> 任务拆解 -> 子任务合同 -> 执行 -> 交付 -> 聚合
```

任务流回答“谁做什么”。

### 2. 信息流

```text
执行证据 -> 结构化状态 -> 压缩汇报 -> 人类决策信息
```

信息流回答“什么信息应该被谁看到”。

### 3. 控制流

```text
授权 -> 工具访问 -> 操作限制 -> 停止条件 -> 恢复或回滚
```

控制流回答“每一层可以做什么、不可以做什么”。

### 4. 升级流

```text
无法验证 / 边界冲突 / 高风险 / 目标歧义
  -> 停止局部执行
  -> 向上汇报原因、证据、选项和建议
  -> 更高层决策
```

升级流回答“什么时候必须让更高层介入”。

## 子任务合同的最小字段

```text
task_id
objective
inputs
allowed_tools
write_scope
dependencies
acceptance_criteria
stop_conditions
escalation_target
expected_evidence
```

子任务如果无法填清这些字段，往往还不适合交给独立 Agent 并行执行。

## 面向人的最小汇报

```text
当前目标：
总体状态：正常 / 阻塞 / 待决策 / 完成
已经验证的进展：
尚未验证的假设：
已发现的风险：
需要人决定的事：
可选方案与取舍：
Coordinator 的建议：
底层证据索引：
```

压缩不能删除证据索引。人应该能够在需要时下钻到原始交付物与日志。
