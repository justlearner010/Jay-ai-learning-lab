# 失败模式与反例

## 1. 公司角色扮演

### 现象

Agent 被命名为“CEO”、“产品经理”、“工程师”和“QA”，但共享相同上下文、权限和决策范围。

### 后果

产生更多对话和中间文本，却没有真正分离责任、并行工作或提高验证质量。

### 检查

去掉角色名称后，是否还能说清每个 Agent 独有的输入、权限、交付物和停止条件？

## 2. Coordinator 单点瓶颈

### 现象

所有信息都必须经过 Coordinator，它的上下文迅速膨胀，摘要延迟和调度等待抵消了并行收益。

### 缓解方向

- 使用结构化状态而非反复转述全部对话；
- 让可验证的局部结果直接进入产物库；
- 只将差异、风险和决策点传递给 Coordinator；
- 当任务足够简单时删除 Coordinator。

## 3. 信息压缩失真

### 现象

Coordinator 为了让汇报简洁，删除了不确定性、反对证据或局部失败。

### 缓解方向

- 强制区分已验证事实、假设、风险和建议；
- 保留原始证据索引；
- 定期抽查摘要与原始证据的一致性；
- 不用单一置信度数字掩盖具体不确定性。

## 4. 过度升级

### 现象

Coordinator 缺乏足够的授权或规则，普通局部取舍也频繁上报给人。

### 后果

人仍然是每个子任务的实际调度者，层级只增加了一层转发。

### 检查

每次升级后都问：这是真的需要人的价值决策，还是可以在下一版规则中授权的普通操作？

## 5. 升级不足

### 现象

Coordinator 为了显得自主或降低中断数，自行处理了高风险、越权或目标歧义。

### 后果

表面上人的介入次数很低，实际上系统正在积累未被看见的方向风险。

### 缓解方向

将“没有中断人”与“正确地没有中断人”分开测量。

## 6. 角色漂移和越界

### 现象

Specialist 在执行时重新解释总目标，修改了其他 Agent 的产物，或扩大自己的任务范围。

### 缓解方向

- 子任务合同中明确写入范围和停止条件；
- 在工具层实施权限隔离，而不只在 prompt 中提醒；
- 超出范围的发现作为建议上报。

## 7. 重复劳动与责任空白

### 现象

任务边界重叠时，多个 Agent 重复执行；边界之间存在缝隙时，所有 Agent 都认为某个问题属于别人。

### 缓解方向

- 每个交付物只设一个直接责任 Agent；
- 审查者与执行者可以多个，但最终交付责任必须唯一；
- Coordinator 在执行前检查任务覆盖与交叉。

## 8. 虚假共识

### 现象

多个 Agent 基于相同模型、相同训练偏差或相同不完整资料得出一致结论，系统将一致误当成独立验证。

### 缓解方向

将多 Agent 一致意见与外部证据分开；优先使用测试、一手资料、真实执行或可复现数据。

## 9. 共享状态污染

### 现象

一个 Agent 将未验证假设写入共享状态，其他 Agent 将其当成事实继续执行。

### 缓解方向

- 共享状态标注信息类型：事实、假设、决策、风险、证据；
- 记录来源、时间和验证状态；
- 对关键状态使用版本或不可变事件记录。

## 10. 协调税超过收益

### 现象

多 Agent 的上下文复制、等待、摘要、评审和合并耗费了比实际执行更多的资源。

### 判断

如果单 Agent 能够在可接受的时间和质量内完成任务，就没有必要为了展示多 Agent 架构而保留层级。
